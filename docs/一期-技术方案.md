## 2. Schema 设计

### 2.1 为什么 Schema 是一期最重要的产物

二期用 Next.js + React 重写，复用的不是代码而是 **Schema**。所以：

- Schema 必须**纯数据**（可 JSON 序列化），不能混函数
- 校验规则、联动条件都要**可序列化**
- 顶层必须带 `schemaVersion`，否则二期没法迁移

### 2.2 类型定义

真源文件：`src/core/schema/types.ts`（已实现，改动需同步本节）

```ts
export const FIELD_TYPES = [
  'input', 'textarea', 'number',
  'select', 'radio', 'checkbox', 'switch', 'date',
  'upload', 'subform', 'divider',
] as const

export type FieldType = (typeof FIELD_TYPES)[number]

export interface FormSchema {
  schemaVersion: 1
  id: string
  name: string
  layout: { type: 'single' | 'grid' | 'steps'; columns?: number }
  fields: FieldNode[]
  submit?: { text?: string; successMsg?: string }
}

export interface FieldNode {
  id: string                 // 设计器唯一 key（nanoid），用于选中与列表 diff
  name: string               // 提交字段名，同级唯一
  type: FieldType
  label: string
  props: FieldProps          // 松散可选包，见下
  rules: Rule[]              // 可序列化的校验规则
  visibleWhen?: Condition    // 可序列化的联动条件
  children?: FieldNode[]     // 仅 subform
  layout?: { span: number }  // grid 跨列
}

export interface FieldProps {
  placeholder?: string
  defaultValue?: unknown
  options?: { label: string; value: string }[]
  multiple?: boolean
  rows?: number
  min?: number
  max?: number
  step?: number
  accept?: string
  maxSizeMB?: number
  maxCount?: number
  columns?: number
}

export type Rule =
  | { type: 'required'; message?: string }
  | { type: 'pattern'; value: string; message?: string }
  | { type: 'range'; min?: number; max?: number; message?: string }
  | { type: 'len'; min?: number; max?: number; message?: string }

export interface Condition {
  field: string
  op: 'eq' | 'neq' | 'in' | 'empty' | 'notEmpty'
  value?: unknown
}
```

### 2.3 四条设计红线

| 红线 | 做法 | 工程价值 |
|---|---|---|
| 字段属性不建专属类型 | `props` 松散可选包 + 元数据注册表 | 新增字段类型不改 Schema → 对应"节点动态渲染、零发版"的真实经验 |
| 规则数据化 | `Rule[]` 而非函数 | 能序列化、能导入导出、二期直接复用 |
| 联动结构化 | `Condition` 而非表达式字符串 | 杜绝 `new Function`，安全边界可讲 |
| 版本号前置 | 顶层 `schemaVersion` + `migrate()` | 二期换引擎的抓手 |

### 2.4 校验分层

| 层 | 工具 | 校验对象 | 失败表现 |
|---|---|---|---|
| 结构层 | `zod` | 导入的 JSON 是否符合 `FormSchema` | 定位到 `fields[3].props.options`，画布不崩 |
| 值层 | `async-validator`（Element Plus 内置） | 用户填写的值 | 字段红字 + 阻断提交 |

**为什么不全用 zod**：两者校验对象不同。混用会导致"schema 坏了"和"用户填错了"无法区分提示，且 zod 不适合做字段级异步校验。

### 2.5 值的路径寻址

表单值统一存 `Record<string, unknown>`，子表单值是对象数组。

```
getByPath(model, 'employees[0].name')   // 支持数组下标 + 深层嵌套
setByPath(model, path, value)           // 非法路径返回 undefined，不抛错
```

一套逻辑两处复用：运行时取值 + `el-form` 嵌套校验的 `prop` 路径串。

├─ .github/workflows/deploy.yml   # Pages 部署（verify 通过才构建）
├─ .opencode/commands/            # AI 编码用的斜杠命令

├─ src/
│  ├─ core/                       # 框架无关层（二期整块搬走）
│  │  ├─ schema/{types,zod,factory,migrate}.ts
│  │  ├─ meta/field-meta.ts       # 字段元数据：驱动物料区 + 属性面板
│  │  ├─ engine/{path,validate,visibility,submit}.ts
│  │  └─ io/{import,export,share}.ts
│  ├─ components/fields/          # 每种字段类型一个组件
│  ├─ components/renderer/        # FieldRenderer / RecursiveForm
│  ├─ views/Designer/             # MaterialPanel / Canvas / PropertyPanel / Toolbar
│  ├─ views/Preview/              # /#/f 填写页
│  ├─ stores/designer.ts          # Pinia + 历史栈
│  ├─ router/index.ts             # hash 路由
│  └─ styles/main.css
└─ tests/                         # 只测 core 纯函数

**为什么不用 monorepo**：拆 workspace 要额外解决构建、路径、发布三件事，与"3 周上线"冲突；`core` 用 ESLint 强制无框架依赖，逻辑隔离已经达成。上线后有余力再拆包（正好是第二个技术点）。

## 5. 渲染架构

```
MaterialPanel ──drop──> Canvas ──render──> FieldRenderer ──> components/fields/*
      │                    │                     │
      └── field-meta ──────┴── PropertyPanel     └── core/engine（校验/联动/路径）
```

- **同一组件双模式**：`FieldRenderer` 通过 `designMode` 区分设计态（disabled + 遮罩 + 点击选中）与运行态（正常 v-model）。避免写两套 UI。
- **递归**：`<component :is>` + `provide/inject` 传表单上下文；`subform` 递归渲染子字段。
- **元数据驱动**：`field-meta.ts` 声明每种类型用什么图标、默认 props、属性面板显示哪些配置项。加字段类型只改这一个文件。

## 6. 设计器状态与历史

```ts
commit(fn)  // 所有写操作唯一入口
  → structuredClone(schema) 入 past
  → 执行 fn
  → 清空 future
  → past 长度 > 50 时丢最旧
```

- 选**整树快照**而非 patch 增量：subform 嵌套下增量要做路径 diff + 冲突合并，成本高于收益；100 字段 schema ≈ 50KB，50 份 ≈ 2.5MB 可接受。
- 属性面板输入必须 **debounce 300ms** 或 `@change` 提交，否则打一行字产生 20 条历史。

## 7. 存储与分享（零后端）

| 场景 | 方案 | 键 / 格式 |
|---|---|---|
| 设计器草稿 | localStorage | `fb:schema:<id>` |
| 分享 | URL 编码 | `/#/f?d=<lz-string compressToEncodedURIComponent>` |
| 提交 | localStorage + 结果页 | `fb:submissions` 追加 `SubmitPayload` |

- **长度守卫**：编码后 > 6000 字符时提示"表单过大，请改用 JSON 导入"，**不静默截断**。
- **SubmitAdapter**：`submit(payload)` 一期用 Local 实现，二期换真接口时调用方零改动。

### 已知限制（README 里要如实写）

1. 提交数据只在本机，换个浏览器看不到——这是纯前端的必然代价。
2. `upload` 只记录文件名 + 前端校验大小/类型，不做真上传。
3. 分享链接长度受浏览器/IM 工具限制，大表单走 JSON 导入。

| 项 | 地址 |
|---|---|
| **线上地址（主）** | https://liuyapeng00.github.io/form-builder/ |
| 表单填写页 | https://liuyapeng00.github.io/form-builder/#/f |
| 仓库 | https://github.com/LiuYapeng00/form-builder |
| 备用地址 | 待 T26（Cloudflare Pages / OSS） |

> 命名规则：`https://<用户名小写>.github.io/<仓库名>/`。T03 已验证：首页与 `/#/f` 均可访问，资源路径带 `/form-builder/` 前缀，console 无报错。

### 8.1 GitHub Pages 四个必踩坑

1. `base` 必须为 `/<repo>/`，通过 `VITE_BASE` 注入；硬编码会导致本地开发 404
2. 只能 hash 路由，`createWebHistory` 刷新即 404
3. workflow 权限要 `pages: write` + `id-token: write`
4. 国内访问时通时断

### 8.2 部署链路

`push main` → `pnpm install --frozen-lockfile` → **`pnpm verify`**（带 `VITE_BASE=/<repo>/`，其内部的 build 即部署产物）→ `upload-pages-artifact` → `deploy-pages`。

verify 与 build 合并成一步：verify 已含 build，分开跑会构建两次。`VITE_BASE` 必须挂在这一步上，否则 `dist` 是不带子路径的那次构建，线上资源全 404。

pnpm 版本只认 `package.json` 的 `packageManager`，`pnpm/action-setup` 不要再写 `version`，两处声明会直接报 `ERR_PNPM_BAD_PM_VERSION`。

### 8.3 首次上线需要手动做的两件事（已完成 2026-10-27）

1. 在 GitHub 建仓库并 `git remote add origin`，push `main`
2. 仓库 Settings → Pages → Source 选 **GitHub Actions**

### 8.4 备用地址（强烈建议）

自己的判据是「任何人点开都能用」。同一份 `dist` 用根路径 base 再部署一份到 Cloudflare Pages / 阿里云 OSS，README 主备并列。成本约 10 分钟。

## 9. 风险与降级

| 风险 | 概率 | 降级方案 |
|---|---|---|
| 子表单嵌套拖拽不稳（Sortable 嵌套已知问题） | 中高 | 子表单内改为"选中容器 → 属性面板添加子字段"，主功能不受影响 |
| 属性面板吃时间无底洞 | 高 | 只做 4 类配置（基础/选项/校验/联动），样式配置一律不做 |
| 国内打不开 Pages | 中 | 备用地址（§8.4） |
| 范围蔓延（想加审批流/版本化） | 中 | 硬规则：一期上线前不接任何额外功能 |
| 分享链接超长 | 中 | 长度守卫 + JSON 导入兜底 |
